# 系统架构

## 组件

| 组件 | 职责 | 是否持有数据库凭证 |
|---|---|---|
| Agent / MCP 客户端 | 提交 SELECT 意图、轮询状态并获取自身查询结果 | 否 |
| MCP Server | 面向 API 的轻量级身份验证 HTTP 客户端 | 否 |
| API | 验证 Agent/Reviewer 身份、校验请求、持久化提案、提供状态/审核接口 | 否 |
| Worker | 认领提案、解析数据源密钥、再次校验、规划查询、在原生只读事务中执行并持久化结果 | 是，仅限所需数据源 |
| Proposal Store（提案存储） | 持久化提案生命周期和审计事件 | 不持有目标数据库凭证 |
| Reviewer（审核员） | 审核查询、用途和风险快照；附带原因批准或拒绝 | 仅持有审核令牌 |

## 提案生命周期

```text
Agent 提交
     |
     v
 ANALYZING
     |
     | Worker 使用唯一 fencing token 原子认领
     v
ANALYZING_WORKER
     |
     +---- 校验/对象/只读模式失败 ----------> BLOCKED
     |
     +---- 低风险且所有自动门禁通过 --------> 在已认领状态下执行
     |                                           ANALYZING_WORKER
     |                                                |
     |                                            SUCCEEDED
     |
     +---- 需要人工审核 ---------------------> PENDING_APPROVAL
                                                   |
                                                审核员决策
                                                /       \
                                           REJECTED    APPROVED
                                                          |
                                                  Worker 使用新的
                                                  fencing token 认领
                                                          |
                                                     EXECUTING
                                                          |
                                             重新校验/重新规划/风险比较
                                                  /             \
                                         BLOCKED 或重新审核       执行
                                                                  |
                                                              SUCCEEDED
```

过期任务认领会被恢复到 `ANALYZING` 或 `APPROVED`。租约恢复时会清除之前的 fencing token。每次 Worker 写入都必须检查当前 token 和预期状态，确保旧进程无法在任务被转交后发布结果。

## 执行门禁

在执行用户 SQL 之前，Worker 必须：

1. 检查提案是否过期、请求者是否有权限，以及存储的查询/参数哈希是否匹配。
2. 使用所选数据库方言重新解析 SQL。
3. 在新连接上验证数据库原生只读能力。
4. 在数据库目录中解析所有被引用对象，并且只接受受支持的基表对象。
5. 在安全的情况下运行有界 EXPLAIN；Oracle 的 EXPLAIN PLAN 会写入 `PLAN_TABLE`，因此有意跳过。
6. 重新计算风险并与审批快照比较。任何变化都会使原审批失效。
7. 执行前再次确认 Worker 仍持有当前 fencing token。
8. 在具备时间和资源限制的数据库原生只读事务中执行。
9. 限制结果行数和序列化后的结果字节数，重置或使连接失效；只有在任务认领仍有效时才允许发布结果。

## 持久化

当前阶段保留 SQLite 作为单节点状态库：一个 API 和一个 Worker 在同一客户主机读写同一本机文件。状态变更和审计写入在同一事务中完成，任务认领使用 `BEGIN IMMEDIATE` 实现单机 CAS/fencing 行为。不要把 SQLite 文件放到网络共享文件系统，也不要让多个主机共享写入。需要多主机、多 Worker 或高可用横向扩容时，再迁移 PostgreSQL/队列并保留原子任务认领、fencing token 校验、租约恢复和事务内审计写入。

## 安全边界

原生只读事务约束的是当前事务，并不能让高权限数据库账号变得安全。必须使用最小权限数据库账号，移除 MySQL 创建临时表的权限，限制网络出口，并确保 API/MCP 与数据库密钥隔离。

表白名单不等同于行级或列级控制。在投入生产前，仍需实现敏感列策略、租户/行级过滤、数据脱敏、凭证轮换、速率限制、外部不可篡改审计存储，以及生产级身份验证。


## 下一阶段目标架构：客户内网 Worker（C1）

本项目下一阶段采用“云端控制面 + 客户内网执行面”。详细决策见 [ADR-0001：客户内网 Worker 执行架构](adr/0001-customer-network-worker.md)。

目标请求路径：Codex / Agent 通过 HTTPS / OAuth 连接 SafeDB 云端 MCP Gateway；云端 API、审批和 PostgreSQL 调度服务创建任务；客户 Worker 主动通过 mTLS HTTPS 领取任务并回传状态和受限结果；Worker 在客户内网通过本地凭证管理组件连接客户业务数据库。

### C1 的职责边界

- 云端负责 Agent 身份、租户与数据源授权、提案、审核、任务调度和审计索引。
- 客户内网 Worker 是唯一持有目标数据库凭证并连接业务数据库的组件。
- Worker 主动建立到云端的出站安全连接；云端不连接客户数据库，也不向客户 Worker 开放入站管理端口。
- Worker 不应直接连接公网暴露的控制面 PostgreSQL；任务经由经过认证、租户绑定且具备租约/fencing 保护的 HTTPS 协议交换。
- 每个客户或信任域使用独立 Worker 实例/隔离池，不共享凭证、连接池或进程内秘密状态。

### 人工堡垒机凭证

当前堡垒机只能人工生成约 8 小时有效的临时连接串，尚无自动申请/续期 API。因此 C1 不实现伪自动续期，而是提供客户内网的本地凭证录入流程：

1. 管理员人工从堡垒机获取临时连接串。
2. 管理员在客户 Worker 主机通过本地 CLI 或受控内网管理入口录入，不经过云端。
3. Worker 记录凭证版本和有效期等非敏感元数据，并通过客户 Vault/OS 密钥存储管理凭证；首个可控版本也可使用内存模式，重启后重新录入。
4. 到期前提醒管理员；到期后停止该数据源的新任务并报告 NEEDS_CREDENTIAL。
5. 管理员录入新凭证后，Worker 验证连接、切换连接池并恢复处理。无需修改 YAML 或重启整个系统。

凭证值不得进入云端、YAML、Agent/MCP 配置、命令行参数、环境变量、shell history 或日志。C1 的 SQL、参数和受限结果仍可能经过云端；不能把 C1 描述为数据完全不离开客户网络。

**重要兼容性检查：** 必须确认堡垒机返回的连接串能从计划部署 Worker 的内网主机直接访问。如果它依赖操作者电脑上的 localhost SSH 隧道或设备绑定，则需把 Worker 部署到相应主机，或由客户提供受控内网隧道/代理。

当前仓库已实现 Worker 本机凭证 CLI、进程内存凭证管理和 loopback Web 管理面板；尚未实现远程 Worker 协议、远程 MCP、多租户 OAuth 或云端控制面。完整 C1 仍是目标设计，不是现有功能。项目仍为安全原型。


## 当前推荐部署形态：单节点客户内网部署

为优先获得可部署、可运维的可靠方案，当前阶段保留 SQLite，不提前引入 PostgreSQL 或跨主机队列。推荐一台客户控制的主机运行 API、单个 Worker 和本机 SQLite；MCP 客户端通过客户批准的网络/VPN 连接 API。Worker UI 只在这台主机的 localhost 开放。

- API 与 Worker 共享同一台主机上的 SQLite 文件；SQLite 使用本地持久化磁盘。
- 单节点限定一个 API 实例和一个 Worker 实例；不通过 NFS/SMB 共享 SQLite。
- Worker UI 在 `127.0.0.1:8090` 提供本机凭证管理页面；Compose 映射只绑定宿主机 loopback。
- Worker 本地凭证仍只驻留进程内存；UI 登录密码哈希也只在 Worker 进程内存。二者在 Worker 重启后需重新设置/录入。
- 若未来需要云端集中控制、多客户多 Worker 或高可用横向扩容，再迁移为 PostgreSQL/队列和出站 Worker 协议；当前不为未实现的 SaaS 需求引入分布式复杂度。
